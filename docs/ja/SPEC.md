# プロダクト仕様 — Travel Discovery

Travel Discovery のプロダクト仕様。アプリが何をするか、誰のためのものか、MVP で何を扱わないかを定める。プロダクトを変更する人や、変更が仕様に合っているかを確かめる人に向けた文書だ。要件をどう実現しているかは[アーキテクチャ](ARCHITECTURE.md)、[データモデル](DATA_MODEL.md)、[診断アルゴリズム](DIAGNOSTIC_ALGORITHM.md)にある。

- バージョン: 0.1
- 状態: 初期実装のベースライン
- 種別: 個人プロジェクト／公開 Web アプリ
- アプリの言語: MVP から日本語（`ja`）・英語（`en`）・スペイン語（`es`）、Phase 17 からフランス語（`fr`）も。既定のロケールは日本語。

## 1. プロダクトの目的

短く変化のあるクイズを通じて、ユーザーが自分に合う海外の旅行先を見つけられるようにする。都市・地域単位の旅行先を 3〜5 件推薦し、合う理由を説明する。目安の費用を示し、航空券・ホテルの検索にリンクする。

見た目は洗練されていて、触って楽しいものにする。同時に、理解しやすく、テストしやすく、運用コストが低く、将来ソースコードを公開できる状態を保つ。

## 2. 対象ユーザーと主な利用の流れ

1. ランディングページを開く。
2. 任意で旅行の条件を設定する: 出発都市・空港、おおよその旅行時期、旅行日数、予算の範囲、その他の関連する条件。
3. AI アシストを使うかどうかを選ぶ。このトグルは UI 上に見えていて、既定は OFF。
4. 動的に選ばれた質問（通常は 10 問前後）に答える。
5. 順位つきの旅行先 3〜5 件を見る。各旅行先には適合スコア、理由、見どころ、注意点、おすすめの日数・季節、目安の予算、検索リンクがつく。
6. 後のフェーズで、任意で AI に推薦を言い換え・説明させたり、限られた追加質問をしたりする。

アカウントは不要。MVP では個々の回答や診断履歴をサーバーに保存しない。

## 3. 範囲

### MVP / P0
- 日本語・英語・スペイン語・フランス語にローカライズしたレスポンシブな公開 UI と、目に見える言語切り替え。
- ランダムな変化と適応的な選択を備えた、質問による診断。
- AI に依存しない決定的な TypeScript で実装した、中核のスコアリングと順位付け。
- 国に紐づく都市・地域単位の旅行先の結果。
- D1 に保存するコンテンツデータとマイグレーション。
- 現行の公式ドキュメントを確認したうえで選ぶ、Cloudflare のアクセス制御によるパスワードレス／マネージドな管理者アクセス。
- 質問、選択肢、スコアへの効果、旅行先、旅行先の属性、全体設定の管理画面での CRUD。
- ユーザーに見える AI アシストのトグル。既定は OFF。
- 有効で利用できるときの、AI による推薦理由の説明。
- AI が無効・利用不可・レート制限中・検証不合格のときの、決定的なフォールバック説明。
- 外部の航空券・ホテル検索へのリンク。リアルタイム価格とは連携しない。
- スコアリング・質問選択・API 検証の単体テストと、主な流れと管理者認可の E2E テスト。
- README、アーキテクチャとデータモデルの文書、`.env.example`、CI チェック、デプロイ手順。

### MVP の範囲外
- ユーザーアカウントやプロフィール。
- 個人のクイズ回答や履歴のサーバー保存。
- 航空券・ホテルのリアルタイム価格や予約。
- 決済、アフィリエイトのトラッキング、収益化。
- AI による旅行先の順位付け。
- 検証せずに示す AI 生成の事実。
- ネイティブのモバイルアプリ。
- 一般公開の登録や、複数管理者のロール管理。

## 4. クイズの挙動

- 目標の問題数: 10 問。
- 設定できる上下限の初期案: 最小 6、最大 12。初期値で、管理者が変えられる。
- 質問は有効・公開済みのものからだけ選ぶ。
- 1 回のセッションで同じ質問を繰り返さない。
- セッションごとに組み合わせを変える。
- 質問のカテゴリーのバランスを取る。その時点で有力な旅行先を見分けられる質問や、好みのシグナルの空白を埋める質問を優先する。
- それまでの回答に応じて次の質問を変える。
- 最小数に達し、文書化した終了ルールが十分なシグナルを得たと判断したら終える。最大数では必ず終える。
  - 文書化したルールは目標の問題数だ（[DIAGNOSTIC_ALGORITHM.md](DIAGNOSTIC_ALGORITHM.md) §8）。
  - 結果が安定したら終える方法は Phase 15 で評価し、採用しなかった。
- ユーザーは前に戻る、回答を直す、やり直す、進捗を見る、ができる。
- 有効な質問が足りないときは、質問数を減らしてはっきりしたメッセージを出す。決してクラッシュしない。
- テストできるシード付きの乱数の方針を使う。テストを制御できない乱数に依存させない。

### 初期の質問タイプ
- 単一選択。
- 複数選択は、スコアの意味がはっきり定義されている場合だけ。
- 数値・範囲のスライダーは、予算のように範囲が明確な値に限る。
- MVP では自由記述の回答を中核のクイズに含めない。後の AI チャットは独立した任意の機能にする。

## 5. 旅行の条件

ハードな条件と好みのスコアは区別する:
- 出発地・空港（任意だが検索リンクに役立つ）。
- おおよその旅行日数。
- 入力された場合は、旅行時期または季節。
- 入力された場合は、予算の範囲と通貨。
- その他の条件は、プロダクト上の明確な必要があるときだけ足す。

未入力の値をゼロとして扱わない。費用や季節の情報が足りないまま推薦しているときは、そう説明する。

## 6. スコアリングと推薦

- 各旅行先は、文書化した尺度（初期案: 0〜5）で属性スコアを持つ。
- 回答の選択肢は、1 つ以上の属性に重みつきの効果を与える。
- スコア計算は純粋関数にし、単体テストを持たせる。
- ハードフィルターは、明示的に入力されたハードな条件にだけかける。それ以外はソフトな適合スコアを使う。
- 表示する前に、スコアを文書化した比較できる範囲に正規化する。
- データが許す限り 3〜5 件の旅行先を返す。条件に合う旅行先が少ないときは、説明を添えて少ない件数を返す。
- 同じ回答と旅行先データなら、同点の扱いは決定的でなければならない。
- いちばん合う旅行先は必ず最初に出す。残りの枠は、ほぼ同じくらい合う旅行先から、クイズのセッションのシードで選んでよい。そのため結果はクイズごとに変わりうる。「ほかの候補を見る」で、その中から引き直す。同じ回答、データ、シードなら結果は同じで、適合度とその順は決定的なままだ（ADR-037）。
- スコアは現在のコンテンツデータに基づく相対的な適合度で、客観的な確率や保証ではないと明示する。
- AI は選ばれた旅行先を説明してよいが、順序・スコア・対象可否・事実を変えてはならない。
- すべての旅行先に、人が書いたフォールバック説明を用意する。

## 7. 旅行先のコンテンツ

旅行先は国に紐づく都市または地域だ。各旅行先は次を持てるようにする:
- 安定した ID／スラッグ。
- 表示名と国への参照。
- 概要と見どころ。
- 旅のスタイル／属性スコア。
- おすすめの旅行日数。
- ベストシーズンの目安。
- 注意点・制約。
- 目安の費用の範囲と、その通貨、対象範囲、基準、出典、最終更新日。
- 画像の URL、画像のクレジット・出典、代替テキスト。
- 結果の地図に使う代表地点（緯度と経度、任意）。[DATA_MODEL.md](DATA_MODEL.md) の「Phase 20 のスキーマに関する注記」を参照。
- 検索リンクの設定、または安全なリンク生成の方針。
- 公開状態とタイムスタンプ。

現在の旅行価格をでっち上げない。シードデータに例示の概算を入れてよいのは、そう明記し、出典・基準・日付を記録した場合だけ。当初は手作業で管理する範囲を優先する。

### 結果の地図（Phase 20）

結果ページには、表示中の結果を載せた世界地図を 1 枚出す（[DECISIONS.md](../working/DECISIONS.md)（英語のみ） ADR-036）。

- ピンの番号は結果の順位と一致させる。位置のない結果は地図に載せず、地図の下に名前を挙げる。
- 地図は結果の一覧を補うものだ。代替テキストで地図上の各旅行先と国を挙げ、ピンは操作の対象にせず、ホバーに頼る操作は置かない。
- 陸地は、パブリックドメインの Natural Earth のデータから描いた静的な SVG で、アプリ自身が配信する。タイルサーバー、地図 API、キー、外部へのリクエストは使わず、質問のページでは地図を読み込まない。
- 位置のある結果には、Google マップを新しいタブで開くリンクを付ける（Maps URLs: `https://www.google.com/maps/search/?api=1&query=<lat>,<lng>`）。リンクで渡すのは座標だけで、回答や条件は渡さない。

## 8. AI アシスト

- ユーザーは UI で明示的に AI アシストを選ぶ。既定は OFF。
- OFF のときは AI にリクエストしない。
- ON のときも、決定的なクイズと順位付けが先に動く。
- AI には必要最小限のデータだけを渡す: 旅行先のコンテンツと、関連する回答の短い要約。各旅行先のデータは適合度や順位によらず同じ形で、各ノートはほかの旅行先に触れずに、その旅行先だけを説明する。
- MVP では AI は説明文だけを生成し、旅行先の選択や順位付けはしない。
- レスポンスのスキーマを検証し、長さの上限をかける。
- ユーザー入力と旅行先のテキストはすべて信頼できないデータとして扱い、指示として扱わない。
- 秘密情報、システムプロンプト、内部のスタックトレース、プロバイダーのエラーを見せない。
- サーバー側でリクエストを制限し、エラーは利用者を妨げない形で処理する。
- AI が利用不可・上限超過・不正な出力のときは、決定的なフォールバックと、操作を妨げない通知を出す。
- 検証に通らなかったノートは、そのノートだけを捨てる。ほかの旅行先のノートは残し、ノートのない旅行先は決定的な説明だけをエラーなしで表示する。
- AI の上限と提供状況は、使えると約束せずに示す:
  - 利用者ごとの上限をトグルの横に書く。
  - サイト全体で AI を止めているときはそう伝え、トグルを無効にする。
  - 上限に達したときは、どの上限か、いつまた使えるかを伝える。利用者ごとの上限とは別に、全利用者の合計の 1 日の上限に達すると、UTC のその日の残りは AI を使えない。
- 実装時に、Cloudflare Workers AI の現在の無料枠、対応モデル、規約、互換性を確認する。サービスが無料であり続けると約束しない。

## 9. 航空券・ホテル検索のリンク

- 航空券とホテルの検索サービスへの外部リンクを出す。
- 実装時に確認した、文書化された安定した URL パラメーターか、公式のパートナー／ディープリンク形式だけを使う。
- 検索パラメーターを安全にエンコードできないときは、条件が入力済みのように見せず、サービスの検索ページにリンクする。
- 検索サイトをスクレイピングしない。
- MVP では予約、価格保証、アフィリエイト ID、リアルタイムの空き状況を扱わない。
- 外部リンクは安全に開き（`rel`／target を適切に設定）、アプリを離れることをユーザーに明示する。

## 10. 管理コンソール

管理者ができること:
- 質問と旅行先の一覧・検索・絞り込み。
- 質問の作成・編集・無効化。
- 質問の選択肢と、重みつきの属性への効果の管理。
- 旅行先と属性スコアの作成・編集・無効化。
- 目安の費用のメタデータと、出典・更新日の更新。
- できる範囲での、公開前の変更のプレビュー。
- 検証済みの範囲内での、クイズの最小・最大問題数と結果件数の変更。

管理画面の要件:
- UI のルートとすべての管理 API エンドポイントを保護する。
- 入力をサーバー側で検証する。
- クライアント側で隠すことや、見つかりにくさに頼らない。
- 他のレコードから参照されるコンテンツは、論理削除・無効化にする。
- 検証エラーを役立つ形で表示する。
- 機密でない管理操作のメタデータは、必要なときだけ記録する。秘密情報やクイズの回答全体はログに残さない。

## 11. 国際化とローカライズ

- MVP で日本語（`ja`）・英語（`en`）・スペイン語（`es`）に対応し、Phase 17 からフランス語（`fr`）にも対応する。
- 初回訪問時は日本語にする。ロケールを保存するなら、ユーザーの UI 設定だけをローカルに保存する。アカウントを求めたり、不必要にサーバーへ送ったりしない。
- 目に見えて、キーボードで操作できる言語セレクターを用意する。
- 次をローカライズする:
  - 公開画面と管理画面の UI ラベル、ボタン、ナビゲーション、フォームの検証、読み込み中・エラー・空の状態
  - クイズの質問・選択肢と、旅行先の名前・説明・見どころ・注意点
  - 費用のラベルと、AI 説明の指示と出力
- ロケールファイルと安定した翻訳キーを使う。ハードコードした UI 文字列をコンポーネントに散らばらせない。
- ロケールに合わせた数値・日付・通貨の書式を使う。
- 安定した ID とスラッグは、翻訳したラベルとは別に保存する。
- 中核のコンテンツを実行時の機械翻訳に頼らない。シードしたコンテンツの翻訳は人が整える。
- 選択した言語のコンテンツがないときは、文書化した 1 つのフォールバック方針に従い、必要な箇所ではそれを明示する。
- 文書の言語メタデータを適切に設定し、言語を切り替えたら更新されるようにする。

## 12. アクセシビリティと UX

- モバイルファーストのレスポンシブなレイアウト。
- キーボード操作と目に見えるフォーカス。
- セマンティックなフォームコントロールとアクセシブルなラベル。
- 動きを減らす設定を尊重する。
- 読み込み中、空、エラー、再試行の状態を用意する。
- ユーザーの入力を妨げたり遅らせたりするアニメーションを避ける。
- 動きや AI を無効にしても、主な診断を使えるようにする。
- 状態を色だけで伝えない。

## 13. プライバシーとセキュリティ

- MVP にはアカウントの仕組みも、サーバー側のクイズ履歴の保存もない。
- ユーザーが AI アシストを有効にしない限り、回答を AI に送らない。
- 秘密情報をリポジトリやブラウザーのバンドルに入れない。
- すべての API 入力と AI の出力を検証する。
- AI と管理画面のエンドポイントに妥当なレート制限をかける。
- 本番のエラーメッセージは一般的な内容にとどめる。詳しいエラーは管理されたサーバーログに残す。
- 既定ではアナリティクスや第三者のトラッカーを使わない。
- 外部の画像、AI、検索サービスと、それに伴うデータの流れを文書にする。
- 管理 API の認可は、フロントエンドのルーティングとは別に保護する。

## 14. MVP の受け入れ基準

1. ユーザーがモバイルとデスクトップで、日本語・英語・スペイン語・フランス語のどれでも診断を終えられる。
2. 質問がセッションごとに変わり、1 回のセッション内で繰り返されない。
3. 適応的な選択が、設定した最小・最大の範囲を守る。
4. 同じデータ、回答、セッションのシードなら、順位付けが決定的である。
5. 条件に合う旅行先が十分にあれば、3〜5 件の推薦が表示される。
6. AI トグルが OFF なら、AI へのリクエストはゼロ。
7. AI が失敗しても、推薦を妨げたり変えたりしない。
8. 管理者がコードを変えずに質問と旅行先を編集・公開できる。
9. 認証されていないユーザーは管理 API を操作できない。
10. マイグレーションとシードデータが、空のローカルデータベースから動く。
11. 言語の切り替えが公開画面・管理画面の UI とシードしたコンテンツ全体で効き、翻訳がない場合は文書化したフォールバック方針に従う。
12. lint、型チェック、単体テスト、E2E テスト、本番ビルドが通る。
13. 秘密情報をコミットせずに、文書の手順からデプロイを繰り返せる。
