# Prompt 12 — More attributes and questions for a more varied quiz

The quiz has 12 published questions and asks 10 of them by default (`targetQuestions` 10, `maxQuestions` 12), so almost every quiz shows the same questions in a different order. Destinations are described by 7 attributes only, which limits how different new questions can be and how well the ranking separates destinations. This phase adds attributes and questions so that each quiz draws from a larger pool, and measures the effect. New destinations (Phase 13) and the AI notices and limits in the UI (Phase 14) are later phases. The first response is investigation and a proposal only: no content file, code, configuration, or database change, and no deployment.

Do not run remote Cloudflare commands, deploy, import content, change quiz settings, push, commit, or add, remove, or update dependencies without the owner's explicit approval for that action. Dashboard and admin-console steps on deployed environments are the owner's; describe them, do not perform them. The account must stay on Workers Free: the only accepted charge is the owner's existing domain registration. AI stays disabled in every environment.

If this phase is still open in the first week of December 2026, remind the owner of the dated Workers Logs and Billing check ([OPERATIONS.md](../docs/en/OPERATIONS.md) section 3 "Dated").

## Tasks
1. **Baseline measurement (local, no content change).** Write a small deterministic simulation (a test helper or a script under `scripts/`, Node only, no network) that runs the engine on the current bundle for many seeds (for example 1,000) with seeded random answers and reports: how many distinct question sets appear, the mean pairwise overlap of question sets, how often each question is shown, how often each destination reaches the top `resultCount`, and how many destinations never do. Record the numbers as the baseline in a new "Phase 12 verification log" in `docs/working/DECISIONS.md`.
2. **Attribute proposal (owner review).** Propose 3–5 new attributes (target total 10–12) with a slug, a one-line definition in `ja`, `en`, and `es`, and a scoring rubric that says what 0, 3, and 5 mean. Prefer travel-style preferences a user can state and an editor can judge from general knowledge (for example climate warmth, nightlife, outdoor activity, ease of getting around). Avoid attributes that read as factual or safety claims (crime, health, visa, prices, opening hours) or that would need live data. Explain how each one separates the current 18 destinations, and which new questions would use it.
3. **Scores for existing destinations (owner review).** For each of the 18 published destinations, propose a score for every new attribute with a one-line reason. Scores are editorial judgements (as in ADR-028 `initial-v1.json`), not sourced facts; say so in the review copy. Unscored attributes lower coverage instead of counting as 0 (DIAGNOSTIC_ALGORITHM §3), so every destination should get every new score.
4. **Question proposal (owner review).** Propose new questions to reach about 30 published questions in total, balanced across categories (propose a new category only if needed), with 3–5 options each, `priorityWeight`, and option effects on the existing and new attributes. Check that every attribute is moved by at least three questions in each direction where that makes sense, that no two questions ask the same thing in different words, and that wording is natural in `ja` (polite style of the UI), `en`, and `es` (curated, not machine-translated at runtime). Existing questions cannot be updated by the import (ADR-028: questions with existing slugs are skipped), so propose whether existing questions stay unchanged (recommended unless a clear gap exists) or how a change would be applied, with its risk.
5. **Bundle and checks (after approval of tasks 2–4).** Write `content/initial-v5.json` = `initial-v4.json` plus the approved attributes, scores, and questions, with nothing else changed (check by comparing both files without the new items and fields). Extend `test/node/content-bundle.test.ts` only where needed (for example: every destination scores every active attribute; every attribute is affected by at least one published question). Run the simulation on `initial-v5.json` and record the comparison with the baseline. Provide a rendered review copy of all new and changed texts in the three locales for the owner, and propose whether `targetQuestions` and `maxQuestions` should change, with the simulation numbers; quiz settings are changed only by the owner in the admin console.
6. **Import (owner steps, each approved).** Preview first: record Time Travel bookmarks before and after, run the import with the update mode (new attributes and questions created, destinations updated with the new scores), then check `/api/diagnosis-content` in `ja`, `en`, and `es` against the bundle, run `scripts/check-deployment.mjs`, and answer complete quizzes in all three locales in the built-in browser. Then the same on production. Record bookmarks, counts, and results in the "Phase 12 verification log".
7. **Documentation.** Update ADR-028 (content files) for `initial-v5.json`, [DIAGNOSTIC_ALGORITHM.md](../docs/en/DIAGNOSTIC_ALGORITHM.md) if any behavior or the deferred-selection note changes (the "at least 15 destinations and 2 × `maxQuestions` usable questions" condition may now be met; implementing it is not part of this phase), and the Japanese twins of any changed stable doc.

Deferred, not part of this phase: new destinations (Phase 13), AI notices, limits, and status in the UI (Phase 14), deploying the quota Durable Object to production and production AI, discrimination-based question selection and early stopping, images, a dated exchange-rate table, the out-of-policy Access check, and the pre-public-release checklist.
