# Prompt 25 — New attributes for what the quiz cannot yet tell apart

Approved by the owner as drafted (2026-11-08). Each content change still needs the owner's approval during the phase.

Phase 24 corrected scores but left Rome and Maasai Mara rare (1.2% of top-5 results on random answers, `content/initial-v11.json`). The 11 attributes cannot express what sets them apart: ancient sites separate Rome from other historic cities, and wildlife separates Maasai Mara from other nature destinations. A respondent can already pick "Wildlife on land or in the sea" in `nature-sights`, but that option only moves `nature` and `adventure`. Edinburgh, Copenhagen, and Lisbon are still nobody's ideal ("Phase 24 verification log" in `docs/working/DECISIONS.md`).

This phase adds a small number of attributes, the questions and option effects that use them, and, only if the owner decides after seeing the numbers, a few destinations. The engine (fit formula, ranking, result variety, question selection) and the quiz settings do not change. The first response is the diagnosis and a proposal only: no content file, code, configuration, or database change.

Do not push, commit, deploy, import, change quiz settings, run remote Cloudflare commands, or change dependencies without the owner's explicit approval for that action. A push to `main` deploys production, and a content import is an owner step. AI stays disabled, and the account stays on Workers Free. If this phase is still open in the first week of December 2026, remind the owner of the dated Workers Logs and Billing check ([OPERATIONS.md](../docs/en/OPERATIONS.md) section 3 "Dated").

## Measurement limits to handle first
- **Reach.** A quiz asks about 10 of 29 questions, so an attribute moved by one question stays out of most quizzes and cannot change their results. Report how many quizzes, on random answers and for sparse and anchored respondents, have a non-zero preference on each new attribute.
- **Comparability.** Sparse and anchored respondents are built over all usable attributes (`test/simulation/respondents.ts`), so a new attribute changes the simulated population and who counts as ideal. A difference between `initial-v11.json` and the new bundle mixes the content's effect with this change. Report which comparisons stay valid (random answers, for example), and if needed add a comparison on a fixed population. State the limit next to every number it affects.

## Tasks
1. **Diagnosis (local, no content change).** Starting from the Phase 24 numbers, report for Rome, Maasai Mara, Edinburgh, Copenhagen, Lisbon, and any other rarely shown destination: its nearest competitors, what a traveller would choose it for, and whether an existing attribute already expresses that. Report which existing questions and options already ask about it. Add any measure needed to `test/simulation/` (local only, never part of `npm run check`).
2. **Attribute proposal (owner review).** Propose at most three new attributes. Ancient sites and wildlife are the starting candidates; a third needs a stated reason from task 1. For each: slug, name and one-line definition in `ja`, `en`, `es`, and `fr`, and a rubric that says what 0, 3, and 5 mean. Record the rubrics in the verification log, because the earlier rubrics are not in the repository. Prefer preferences a traveller can state and an editor can judge. Avoid safety, health, visa, price, or live-data claims, and avoid wording that presents animal encounters as guaranteed. Explain how each attribute separates the near-duplicates, and report any overlap with `history-culture`, `nature`, or `adventure`.
3. **Scores (owner review).** Propose a score for every new attribute on all 42 destinations, each with a one-line reason from the rubric or the destination's authored text. Label them as editorial judgements. Do not change existing scores unless the owner approves a listed proposal.
4. **Questions and effects (owner review).** Propose how the new attributes reach enough quizzes, using the reach measure above. Compare two ways, alone or combined: new effects on existing options (for example the `wildlife` option of `nature-sights`) or new options on existing questions (for example `trip-interests`), and new questions, at most one per new attribute. Give texts in four locales and `priorityWeight` for anything new. An import replaces a whole question and must list every active option it has in the database (OPERATIONS.md section 8). Do not ask the same thing twice in different words.
5. **Simulation (owner decides what to keep).** Compare `initial-v11.json` with the proposal on: reach; top-5 share spread (highest, lowest, standard deviation); found in the top 5 and first by respondents whose ideal a destination is, per destination; the Phase 15 measures (ideal overlap, ideal first found, fit loss) for sparse and anchored respondents; and question variety. Report every destination whose numbers get worse. Measure each proposed change alone as well as the set, and report the effect of each change before the owner decides on it.
6. **Destination decision (owner, after task 5).** Report whether the new attributes leave gaps that new destinations would fill, with the numbers. Recommend adding none or a short list, at most six. This task stops here if the owner decides against. If the owner approves destinations, follow Prompt 21 tasks 2 to 4: country names, scores on every attribute, four-locale texts, coordinates, and costs and best months only under the approved source rules, left empty when no source meets them. Then repeat task 5 with them included. They go in the same bundle, so production needs one import.
7. **Bundle.** Write `content/initial-v12.json` with only the approved changes on top of `initial-v11.json`, with a test that every other item is unchanged and that every destination scores every active attribute. Prepare a rendered review copy of all new and changed texts in four locales for the owner, kept out of the repository. Rehearse the import locally ("Update existing items", then compare `/api/diagnosis-content` in four locales with the bundle on every field, treating an empty `bestMonths` in the bundle as the API's `null`).
8. **Tests and checks.** Check the new attribute labels where results explain what sets a destination apart, in four locales at phone and desktop width. Run `npm run check` and `npm run test:e2e`. If the billing guard or the deploy guard blocks a check, do not work around it; give the owner the exact command.
9. **Documentation.** A "Phase 25 verification log" with the diagnosis, rubrics, proposals, the owner's decisions, the simulation numbers with their limits, and the rehearsal; ADR-028 content files; DIAGNOSTIC_ALGORITHM.md only if a documented example changes (with the Japanese twin); counts in the README (with its twin) and any stable doc; and IMPLEMENTATION_PLAN.md. The production import and its comparison are owner steps, recorded afterwards.

Not part of this phase: changing the engine or its constants, quiz settings, a region field, images, enabling AI, and source re-checks. If a new attribute turns out to need a schema or code change, stop and ask.
