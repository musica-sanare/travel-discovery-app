# Prompt 14 — AI notices and limits in the UI, and production readiness for AI

AI is disabled in every environment. Preview runs the strict per-client quota in a Durable Object (ADR-029: 5 requests per 60 s and 30 per UTC day, fail closed), which passed its check on preview; production does not have it yet. The public UI shows one "busy" notice for every 429, whether the client hit the window or the daily limit, and the AI toggle gives no hint that AI may be off for the whole site. This phase makes the AI states and limits clear in the UI and prepares production so that enabling AI there becomes a decision the owner can make. Enabling AI on production is not part of this phase unless the owner decides so in task 5. The first response is investigation and a proposal only: no code, content, configuration, or database change, and no deployment.

Do not run remote Cloudflare commands, deploy, import content, change quiz settings, push, commit, or add, remove, or update dependencies without the owner's explicit approval for that action. Dashboard and admin-console steps on deployed environments are the owner's; describe them, do not perform them. The account must stay on Workers Free: the only accepted charge is the owner's existing domain registration. AI stays disabled in every environment unless the owner decides otherwise in task 5, and then only as that decision describes.

If this phase is still open in the first week of December 2026, remind the owner of the dated Workers Logs and Billing check ([OPERATIONS.md](../docs/en/OPERATIONS.md) section 3 "Dated").

## Tasks
1. **Current AI states (local, no change).** List every AI state the public UI can show, from the plan page (toggle and hint) to the results page: off, loading, ready, unavailable (kill switch, timeout, provider error, invalid output, limiter unavailable), rate limited (window and daily limit), and content changed. For each, give the server outcome and status, what the user sees in `ja`, `en`, and `es`, and what the user cannot tell from it (for example which limit was reached, when to try again, or that AI is off for the whole site). Check them locally with the AI endpoint mocked, at 375 px and 1280 px, in light and dark color schemes, without any model call.
2. **Proposal (owner review).** Propose changes to the AI notices, limits, and status, each with the files affected, the API or log contract change (if any, as an amendment to ADR-026 or ADR-029), the privacy impact (ADR-026 B: what is sent, processed, or stored, and for how long), the cost impact on Workers Free, and the tests. Candidates, not decisions:
   - State the limits before use (for example in the toggle hint), without promising that AI is available.
   - Tell the window limit apart from the daily limit in the 429 response and the notice, and say when to try again (the next minute, or after 00:00 UTC in the user's local time).
   - Let the plan page show whether AI is currently available for the site before the user turns it on, and how that status is obtained (cost, caching, and what an unauthenticated client can learn).
   - Record which validation check rejected an `invalid_output` answer as a reason code in the log line, without any request or model content (the trial's `en` rejection is 要確認, "Phase 10 verification log").
   - An app-wide daily cap (ADR-029 "Not covered"), only as an option with its cost and failure behavior.
   Texts are curated in `ja` (the polite style of the UI), `en`, and `es`, never machine-translated at runtime, and never state live facts. The deterministic results stay complete in every state.
3. **Implementation (after approval of task 2).** Implement only the approved changes, with typed translation keys, unit and Workers tests, and E2E tests with the AI endpoint mocked; keep axe passing and no horizontal overflow at 375 px. Provide a rendered review copy of every new or changed text in the three locales before the commit.
4. **Production readiness (owner steps, each approved).** After the code is committed and approved for deployment: deploy the public production Worker with the quota Durable Object and its migration `v1`, with `AI_ASSIST_ENABLED` `"false"` (dry run first), run the check of [DEPLOYMENT.md](../docs/en/DEPLOYMENT.md) 7.2 against production with AI disabled and no model call, and run `scripts/check-deployment.mjs` on production. Deploy the preview Worker first if the code changed since its version `a0b632c4`, and repeat 7.2 there. Ask the owner to read in the dashboard: the `rate_limited` and `disabled` line counts of the checks, the Durable Object requests and rows written, whether the Worker's request count includes the Durable Object calls (要確認 since Phase 11), and that Billing shows no new charge and the plan is still Free. Record versions, times, and results in a new "Phase 14 verification log".
5. **Production AI decision (owner).** Update ADR-026 "Readiness for enabling AI" with the results of task 4 and present each item as met, not met, or 要確認, with a recommendation. Enabling AI on production is a separate owner decision: if the owner decides to enable it, first write the steps (the equivalent of [DEPLOYMENT.md](../docs/en/DEPLOYMENT.md) 7.1 for production, its limits, the stop condition, and how AI is disabled again), and do nothing until the owner approves them; otherwise AI stays disabled and the decision is recorded.
6. **Documentation.** Update ADR-026 and ADR-029 for any contract change, [DEPLOYMENT.md](../docs/en/DEPLOYMENT.md) section 7, [OPERATIONS.md](../docs/en/OPERATIONS.md) sections 3 and 9, [ARCHITECTURE.md](../docs/en/ARCHITECTURE.md) §5 if the AI boundary changes, the root README status, and the Japanese twins of every changed stable doc.

Deferred, not part of this phase: content changes (destinations, scores, questions, costs), discrimination-based question selection and early stopping, images, a dated exchange-rate table, the out-of-policy Access check, removing the overrides (ADR-030), and the pre-public-release checklist.
