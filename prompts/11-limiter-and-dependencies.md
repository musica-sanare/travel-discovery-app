# Prompt 11 — Trial log details, the AI client limiter, and development dependencies

Phase 10 ran the preview AI trial (`docs/en/DEPLOYMENT.md` 7.1). Four of five model calls returned notes, but `AI_CLIENT_RATE_LIMITER` did not refuse any of 15 requests from one address, which blocks production AI (ADR-026 "Readiness for enabling AI", A.2). The per-request log outcomes of the trial were not recorded, and `npm audit` lists high-severity advisories in development-only dependencies. This phase records the missing log details while they are still retained, finds out why the limiter did not refuse requests and fixes it if needed, and updates the affected development dependencies. The first response is investigation and a plan only: no implementation, configuration change, dependency change, or deployment.

The check after the Cloudflare Observability pricing change of 2026-12-01 is **not** part of this phase; it is a dated operations task (`docs/en/OPERATIONS.md` section 3 "Dated" and section 9). If this phase is still open in the first week of December 2026, remind the owner of it.

Do not run remote Cloudflare commands, deploy, roll back, change account settings, push, commit, add, remove, or update dependencies, download browsers, enable AI, or enable any paid plan or feature without the owner's explicit approval for that action. Dashboard and Access changes are the owner's steps; describe them, do not perform them. The account must stay on Workers Free: the only accepted charge is the owner's existing domain registration. After deploying an admin Worker, immediately check without signing in that it redirects to Access; on a 200, redeploy with `workers_dev: false` and report.

## Read first
`CLAUDE.md`, `docs/working/DECISIONS.md` ("Phase 10 verification log", "Phase 7 verification log" for `ADMIN_RATE_LIMITER`, ADR-003, ADR-016, ADR-026 sections A, B, C, "Open decisions", and "Readiness for enabling AI"), `docs/en/DEPLOYMENT.md` sections 5, 6, 7, 7.1, and 9, `docs/en/OPERATIONS.md` sections 2, 3, 4.4, 6, and 9, `worker/index.ts` (AI route and `withinRateLimit`), `server/public/rate-limit-key.ts`, `test/workers/ai-explanations.test.ts`, `test/node/rate-limit-key.test.ts`, and `wrangler.jsonc` / `wrangler.admin.jsonc` (`ratelimits`).

## Tasks
1. **Trial log details (time-critical, owner first).** Workers Free keeps logs for 3 days, so the trial's lines (2026-10-25, 06:18–06:34 UTC) are expected to disappear around 2026-10-28 06:18 UTC. Ask the owner, at the start of the phase, to read in Observability of `travel-discovery-preview` every `ai_explanation` line of that window: `outcome`, `latencyMs`, and `destinationCount` per line, the outcome of the failed `en` request (about 06:26 UTC), and the number of `rate_limited` and `disabled` lines. Record the counts in the "Phase 10 verification log" (no addresses, no request content). If the lines are gone, record that and leave the item 要確認.
2. **Why the AI client limiter did not refuse requests (investigation first).** Re-read the current Rate Limiting binding documentation (limits, `period` values, per-location and eventually consistent counters, behavior on Workers Free, any minimum `limit`, key format and length) and record what changed since the "Phase 4 verification log". Compare `AI_CLIENT_RATE_LIMITER` (5 per 60 s, key from `CF-Connecting-IP`) with `ADMIN_RATE_LIMITER` (120 per 60 s, key from the Access identity), which did refuse requests on preview. Check the key derivation for the addresses Cloudflare actually sends (IPv4 and IPv6 forms) and whether every request from one client really gets the same key, without logging addresses. List the plausible causes with evidence, and propose the smallest change and a verification plan for the owner's decision. Options to weigh include: a test that pins the key behavior, a different limit or period, consulting the limiter before the kill switch so it can be verified with AI disabled (privacy and cost impact stated), and a verification on preview that makes no model calls (empty-body requests never reach the model). Any verification deployment, and any window with AI enabled, needs its own approval; production stays untouched. Record the result in the "Phase 11 verification log", and update ADR-026 A.2, "Readiness for enabling AI", `docs/en/DEPLOYMENT.md` 7.1 if the procedure changes, and `docs/en/OPERATIONS.md` section 9 (with their Japanese twins). AI is disabled in every environment at the end; production AI remains a separate owner decision.
3. **Development dependency advisories.** Run `npm audit` and `npm audit --omit=dev` and list each advisory with its package path, severity, whether it can reach the deployed bundles or Workers, and the fix the registry suggests. Check the current releases and changelogs of the direct dependencies that pull them in (`@cloudflare/vite-plugin`, `@cloudflare/vitest-plugin`, `wrangler`, `drizzle-kit`, and any other), their compatibility with the pinned toolchain (ADR-013), and install scripts under ADR-016. Propose updates that remove the advisories without major-version risks, or record why an advisory is held (as ADR-003 does for `esbuild`). Apply only the updates the owner approves, with the lockfile, and record versions and results in ADR-003 or a new ADR.

Deferred, not part of this phase: production AI, images (privacy and license decision first), a dated exchange-rate table ("Open questions" item 6), checking that an address outside the Access policy is refused (needs a second Cloudflare account), new searches for the other empty costs, and the pre-public-release checklist (`docs/working/PUBLIC_RELEASE.md`).

## Acceptance
- The trial's log outcomes are recorded in the "Phase 10 verification log", or their loss is recorded as 要確認.
- The cause of the missing 429 is identified with evidence and fixed and verified with the owner's approval, or recorded as 要確認 with what was ruled out; ADR-026 "Readiness for enabling AI" and `docs/en/OPERATIONS.md` section 9 reflect the result, and AI is disabled in every environment.
- `npm audit --omit=dev` reports no vulnerabilities; every remaining `npm audit` advisory is either fixed by an approved update or recorded with the reason it is held.
- `npm run check` and `npm run test:e2e` pass after any code, configuration, or dependency change, and the account stays on Workers Free.
