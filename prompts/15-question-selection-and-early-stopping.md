# Prompt 15 — Discrimination-based question selection and early stopping

Production has 30 published destinations, 11 attributes, and 29 published questions (`content/initial-v6.json`), with the quiz settings 6/10/12/5. Questions are drawn by priority, a category balance factor, and a novelty factor ([DIAGNOSTIC_ALGORITHM.md](../docs/en/DIAGNOSTIC_ALGORITHM.md) §7), and the quiz always asks `min(targetQuestions, maxQuestions)` questions unless candidates run out (§8). Discrimination-based selection and stability-based early stopping were deferred until the content was large enough; the condition (at least 15 destinations and `2 × maxQuestions` usable questions) is now met (§8 "Deferred"). This phase evaluates both with local simulations, and implements only what the owner approves, so that the quiz asks questions that separate the likely results and ends when more questions would not change them. The first response is investigation and a proposal only: no code, content, configuration, or database change, and no deployment.

Do not run remote Cloudflare commands, deploy, import content, change quiz settings, push, commit, or add, remove, or update dependencies without the owner's explicit approval for that action. Dashboard and admin-console steps on deployed environments are the owner's; describe them, do not perform them. The account must stay on Workers Free: the only accepted charge is the owner's existing domain registration. AI stays disabled in every environment; enabling it on production follows [DEPLOYMENT.md](../docs/en/DEPLOYMENT.md) 7.3 and is a separate owner decision, not part of this phase.

If this phase is still open in the first week of December 2026, remind the owner of the dated Workers Logs and Billing check ([OPERATIONS.md](../docs/en/OPERATIONS.md) section 3 "Dated").

## Tasks
1. **Baseline (local, no change).** Describe how selection, stopping, and progress display work today, including what the UI shows as the total number of questions and how the AI endpoint recomputes the ranking from the submitted answers. Run `npm run quiz:simulate` on `initial-v6.json` and record the baseline: questions asked, distinct question sets, shared questions, top-5 shares, and destinations that never reach the top 5.
2. **Evaluation method (owner review).** Random answers (the current simulation) say nothing about whether a quiz finds the right destinations. Propose an opt-in, local, deterministic evaluation that adds simulated respondents with a hidden preference profile who answer consistently with it (for example, the option whose effects best match the profile, with a stated rate of noise and skips), and define the measures before running them, for example:
   - agreement of the top `resultCount` with the respondent's "ideal" top results (ranking of all destinations against the hidden profile) and with the result of a full-length quiz for the same respondent and seed;
   - the mean, median, and distribution of questions asked;
   - question variety (distinct sets, shared questions) and the spread of top-5 shares across destinations.
   Say which measures matter most, how the profiles are generated, and the limits of the method (the profiles and the attribute scores share the same editorial model; this is not validation against real travellers). It stays out of `npm test` and `npm run check`, like `quiz:simulate`.
3. **Candidates (owner review).** Evaluate, separately and combined, against the baseline:
   - **Discrimination**: the candidate definition in §8 (standard deviation of each option's effect over the current top `2 · resultCount` destinations, averaged over options, multiplying the current weight), and any variant you consider better (for example a floor so that no question becomes impossible, or a cap on its influence), with the reason.
   - **Early stopping**: the candidate stability rule in §8 (after at least `minQuestions` answers, the top `resultCount` set unchanged over the last two answers and a fit gap of at least 5 points between ranks `resultCount` and `resultCount + 1`), with the thresholds varied.
   For each, report the measures of task 2 and the CPU cost per step in the browser (the domain module also runs on the Worker for the AI endpoint, which must stay within the Workers Free CPU limit; ADR-015). Recommend one option, including "change nothing" if no candidate is clearly better.
4. **Proposal (owner review).** For the recommended option, list:
   - the algorithm change as an update to [DIAGNOSTIC_ALGORITHM.md](../docs/en/DIAGNOSTIC_ALGORITHM.md) §7–§8, keeping selection a pure, reproducible function of content, answers, settings, and seed;
   - the UI change for early stopping: how progress is shown when the total is no longer fixed (for example "Question 3 of up to 10"), the message when the quiz ends early, and whether the user can choose to answer more; texts curated in `ja` (the polite style of the UI), `en`, and `es`, never machine-translated at runtime;
   - any new stop reason or quiz setting (for example a switch or threshold in the admin console), with its validation, defaults, migration if a schema changes, and admin UI labels in the three locales;
   - the effect on the AI endpoint (the server recomputes the ranking from the answers only; confirm that fewer answers stay valid and that `answers.length ≤ maxQuestions` still holds), on stored data (none: answers stay in the browser, ADR-022), on privacy, and on cost;
   - the tests: unit tests for the new functions, the existing determinism and slug-order guarantees, E2E for a quiz that ends early in all three locales, axe, and no horizontal overflow at 375 px.
5. **Implementation (after approval of task 4).** Implement only the approved changes with typed translation keys, unit and E2E tests, and the evaluation of task 2 as an opt-in script. Provide a rendered review copy of every new or changed text in the three locales before the commit. `npm run check` and `npm run test:e2e` must pass.
6. **Deployment (owner steps, each approved).** Deploy the public preview Worker first (and the admin Workers only if the admin console changed), answer complete quizzes in all three locales in the built-in browser, including one that ends early if early stopping is approved, and run `scripts/check-deployment.mjs`; then the same on production. AI stays disabled. Quiz settings are changed only by the owner in the admin console. Record versions, times, and results in a new "Phase 15 verification log" in `docs/working/DECISIONS.md`, together with the baseline and evaluation numbers.
7. **Documentation.** Update [DIAGNOSTIC_ALGORITHM.md](../docs/en/DIAGNOSTIC_ALGORITHM.md), [SPEC.md](../docs/en/SPEC.md) §4 if the quiz behaviour changes, ADR-021 or a new ADR for the decision, [DATA_MODEL.md](../docs/en/DATA_MODEL.md) if a setting is added, the root README status, and the Japanese twins of every changed stable doc.

Deferred, not part of this phase: content changes (destinations, scores, questions, costs), new attributes, enabling AI on production ([DEPLOYMENT.md](../docs/en/DEPLOYMENT.md) 7.3), a manual retry for AI notes, an app-wide AI daily cap, images, a dated exchange-rate table, the out-of-policy Access check, removing the overrides (ADR-030), and the pre-public-release checklist.
